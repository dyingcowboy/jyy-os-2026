## 1. 并发为什么难：执行模型变了

### 1.1 并发、并行与线程

**并发是多个执行流在重叠的时间段内推进；并行是多个执行单元在同一时刻实际执行工作。** 单核也可以通过线程切换实现并发，多核为并行提供硬件条件。

同一进程内的线程共享地址空间、全局数据和堆等资源，各有自己的执行位置、寄存器状态和栈。于是，线程既能方便地通信，也可能互相破坏共享状态。

“每个线程有自己的栈”不表示栈内存被其他线程隔离。局部指针也不等于所指对象私有：两个线程的局部指针可以指向同一块堆内存。

课程线程库的 `spawn(fn)` 创建线程，`join()` 等待已创建的线程结束。等待结束同时建立读取结果所需的同步关系。**函数返回不等于另一个线程完成；创建了线程，也不保证它立即获得 CPU。**

进程通常具有各自的虚拟地址空间；同进程线程共享一个地址空间。这是通信便利程度和隔离方式的重要区别，不应把进程理解成绝对不能共享内存——进程也可以显式建立共享映射。

### 1.2 交错执行只是起点

先采用一个简化模型：把每个线程的操作排成一列，每一步选择一个线程执行它的下一项操作，同时保留各线程内部顺序。

```text
线程 A：A1 → A2
线程 B：B1 → B2

允许的总顺序包括：
A1 → A2 → B1 → B2
A1 → B1 → A2 → B2
B1 → A1 → B2 → A2
```

这里排列的是选定粒度的操作，不能默认“一行 C 源码就是一个原子步骤”。**这个模型用于分析可能发生什么，本身不是消除数据竞争的方法。**

例如，`sum++` 可以抽象成读取、局部加一、写回。初始 `sum = 0`，两个线程各加一次，可以出现：

```text
A 读到 0 → B 读到 0 → A 写回 1 → B 写回 1
```

这叫丢失更新。即使只有一个 CPU 核心，也可能在读与写之间切换线程。**单次读写不可分割，不代表“读取—计算—写回”整体不可分割。**

上述轨迹解释的是简化模型。实际 C／C++ 程序无同步地读写普通共享变量可能已经产生未定义行为，不能把这条轨迹当作其全部可能行为。

### 1.3 Data race 与 happens-before

在这里讨论的 C／C++ 普通对象读写场景中，数据竞争的关键条件是：不同线程访问同一内存位置，至少一个访问是写、至少一个访问不是原子操作，而且两者之间没有 happens-before 关系。

**happens-before 是由语言和同步协议建立的先后关系，不等于“按墙上时钟观察，某次运行里 A 比 B 早”。** 同一线程内的相关顺序、mutex 的释放与后续获取、线程启动和结束等待等，都可以参与建立这种关系。

数据竞争不要求两次访问在物理时间上真正重叠。线程恰好轮流运行，或者人为 `sleep` 一段时间，都不能代替同步。C 标准草案将此类 data race 规定为未定义行为，见 [N1570 §5.1.2.4](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。

“race condition”是更广泛的逻辑概念：程序正确性不当地依赖执行时序。即使全部访问都正确加锁，没有 data race，业务逻辑也可能有竞态。

### 1.4 编译器和 CPU 使简单交错模型不再充分

源码先经编译器变成机器指令，再由 CPU 执行。为了性能，编译器会重写、合并、删除访问，CPU 的缓冲和执行机制也会影响跨核观察到的内存效果。约束来自语言和硬件的内存模型，并非任意乱改。

例如，对一个普通共享变量写：

```c
while (!flag) { }
```

如果另一个线程无同步地写 `flag`，C／C++ 不保证这个循环会持续重新读取并最终看到变化。把变量改成 `volatile` 也不提供通用的线程同步保证，更不会让 `sum++` 变成一个原子操作。

另一种现象即使排除 data race 也存在。假设下面的 `x`、`y` 都是初值为 `0` 的原子变量，四次访问全部使用 relaxed 原子操作：

```text
线程 A                 线程 B
x.store(1, relaxed)     y.store(1, relaxed)
r1 = y.load(relaxed)    r2 = x.load(relaxed)
```

如果要求顺序一致性，即存在一个保留各线程内部顺序、读取符合该总顺序的全局交错，那么 `(r1, r2) = (0, 0)` 不可能发生。它会要求：

```text
A 写 x → A 读 y → B 写 y → B 读 x → A 写 x
```

先后关系不能形成这样的环。但 relaxed 原子操作允许两个读取都得到 `0`。常见硬件解释是：两边的写入都还在本核 store buffer 中，尚未对另一核可见，随后读取便都读到初值。

因此必须区分：**原子性约束一次操作能否被拆开观察；内存顺序约束不同操作之间的顺序和同步关系。** “没有 data race”不能单独推出顺序一致性。[C++ 标准工作草案的原子顺序说明](https://eel.is/c++draft/atomics.order)明确区分了 relaxed 原子性与内存排序保证。

内存屏障主要约束内存操作的顺序，不能把普通的“读取—加一—写回”自动变成一个原子操作。屏障、原子操作和互斥协议需要分别理解。

本阶段能解释这个区别、知道使用正确的 mutex 或原子同步协议即可，不必背每种 CPU 的屏障指令。本文对 `volatile` 的结论针对 C／C++；Java 的 `volatile` 有不同的同步语义，应按 [Java Memory Model](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html#jls-17.4.5)单独理解，且它同样不会自动让 `i++` 整体原子化。

## 2. 互斥：保护操作整体和共享不变量

### 2.1 一把锁究竟保证什么

**互斥锁让遵守同一把锁协议的临界区不能重叠执行，并提供相应的内存同步。** 前一个线程解锁前的写入，对随后成功获取同一把锁的线程建立所需的可见性关系。

```c
pthread_mutex_lock(&m);
sum++;
pthread_mutex_unlock(&m);
```

锁不会自动禁止别人访问 `sum`，也不会暂停整个程序。其他线程只有在尝试获取同一把锁时才受其约束；绕过锁访问，或者改用另一把锁，都可能破坏保护协议。

同一把锁可以被不同线程**先后**持有。`unlock` 后，别的线程才能获取；一次广播不会复制出多把锁。

持锁线程被操作系统调度走，不会自动释放锁。锁的持有权也不意味着线程不会被抢占。

### 2.2 临界区的范围由业务不变量决定

不变量是程序在约定的可观察边界必须维护的约束，例如“余额不能为负”“队列元素数不能超过容量”。临界区内部可以分步更新状态，但不能让其他操作观察或破坏尚未完成的中间状态。

假设余额为 `100`，两个线程各尝试扣款 `100`。下面分别上锁仍然有错：

```text
持锁检查余额 → 解锁 → 持锁扣款 → 解锁
```

两边可能都先检查通过，再分别扣款，最终余额为负。每次余额访问都有锁，但“检查—扣款”没有作为一个整体。

正确的保护范围是：

```c
pthread_mutex_lock(&m);
if (balance >= amount) {
    balance -= amount;
}
pthread_mutex_unlock(&m);
```

**再次拿到锁不会让之前的判断重新成立。** 在锁外保存的 `enough = true` 可能已经过期。这里要保护的是“检查通过后，到扣款前，余额不能被别人改变”。

面试分析代码时，先说明不变量和共享状态，再讨论哪几行需要一起上锁。C++ 等语言中可用 RAII 管理锁的生命周期，避免异常、提前返回等路径漏解锁；它不能替你选择正确的保护范围。

### 2.3 原子操作怎样帮助构造锁

即使 `locked` 是原子变量，这种分开的检查与占有仍然不正确：

```text
等待 locked == 0
把 locked 写成 1
```

两个线程可能都读到 `0`，随后都写入 `1` 并进入临界区。需要把检查与改变状态组合成一个原子操作。

```c
#include <stdatomic.h>

static atomic_int locked = 0;

void spin_lock(void) {
    while (atomic_exchange(&locked, 1) == 1) { }
}

void spin_unlock(void) {
    atomic_store(&locked, 0);
}
```

`atomic_exchange` 原子地写入新值并返回旧值。旧值为 `0` 的线程获取成功；旧值为 `1` 的线程继续等待。上面使用 C 原子操作默认的顺序一致性语义，是教学用自旋锁，不是完整的生产实现。

**CAS（Compare-And-Swap／Compare-And-Exchange）**也是原子的读—改—写操作：只有当前值符合预期时才更新。它可以实现“当前值仍等于我预期的值，才提交修改”，失败后常需要重新读取、计算和重试。CAS 比较的是当前值，不记录这段时间的修改历史。

CAS 能保护一次状态转换，不会自动让多个变量、整段业务操作或内存回收安全；采用 CAS 也不等于整个算法已经满足“无锁”的进展保证。本阶段先理解这条边界，不展开无锁算法的 ABA 和回收协议。

### 2.4 自旋等待、阻塞等待与 futex

| 等待方式 | 等待者在做什么 | 主要取舍 |
|---|---|---|
| 自旋 | 占着 CPU 反复尝试获取 | 短等待可能避免睡眠唤醒开销，长等待会浪费 CPU 并增加争用 |
| 阻塞 | 暂停运行，让出 CPU | 有阻塞、唤醒和调度成本，适合无法很快获得资源的情况 |

如果 A 持锁却被调度走，B 的自旋不会替 A 执行解锁代码。尤其单核时，必须重新调度 A，让它运行到释放点。

mutex 是互斥语义，自旋或阻塞是等待策略，二者不是严格互斥的分类。实际 mutex 可以先尝试用户态原子操作，竞争时短暂自旋或进入内核等待。

Linux 上，futex 提供用户态同步所需的等待与唤醒支持。无竞争时可直接在用户态改变锁状态；确需等待时，内核将“检查值仍符合预期”和“阻塞”原子衔接，以免在检查与睡下之间漏掉状态变化。**不能说每次 `mutex_lock` 都必然发生系统调用。** 见 [Linux futex 手册](https://man7.org/linux/man-pages/man2/futex.2.html)。

### 2.5 为什么加了锁仍有必要使用多线程

锁只让相关临界区互斥，锁外的独立计算仍可以并行。例如，短暂持锁取任务，再到锁外完成较长的计算。

固定工作量下，设单线程耗时为 `T1`，其中必须串行的时间占比为 `s`，其余工作可以理想均分给 `p` 个核心，忽略额外开销：

```text
Tp = T1 × [s + (1 - s) / p]
加速比 = T1 / Tp
p 趋于无穷时，加速比趋于 1 / s
```

这就是 Amdahl 定律的基本模型。单线程 `100 ms` 中有 `10 ms` 必须串行，4 核的理想耗时为 `10 + 90/4 = 32.5 ms`，无限多核心也受这 `10 ms` 限制。

这里的串行占比不是“单线程等锁的时间占比”。串行工作本身无法被分摊，增加线程后，等待可能成为这个限制的表现。真实性能还受缓存、带宽、调度和同步开销影响，公式是明确假设下的分析模型。

## 3. 同步与条件变量：先明确继续执行的条件

### 3.1 互斥与同步分别解决什么

课程在这里区分两类要求：互斥强调“不能同时做”，同步强调“必须先发生某件事，才能继续”。广义上，mutex 本身也是同步原语。

两个线程都正确拿同一把锁，只能限制临界区不重叠，不能指定初始化线程一定先于使用线程获得锁。要表达先后，就需要“初始化已完成”这样的状态条件。

**写同步代码，先写出线程继续执行的谓词，再选择等待工具。** 例如：消费者等待队列非空，生产者等待队列未满，D 任务等待所有前驱完成。

### 3.2 元素、数量、锁、条件变量是不同的东西

“元素”是容器中的一份数据，不是操作系统专有对象。任务队列的元素可以是整数，也可以是包含函数、参数的任务结构体。

```c
int slot;         // 容量为 1 时，存放实际元素的位置
int count = 0;    // 0 表示空，1 表示有一个待领取元素
```

生产者持锁、确认空位后，执行 `slot = 42; count = 1;`。消费者持锁、确认非空后，复制 `int item = slot; count = 0;`。这里整数 `42` 是实际数据，`count` 只是数量。

| 对象 | 职责 |
|---|---|
| 数据元素 | 被放入、取出和处理，例如整数 `42` 或一份任务 |
| 数量／状态变量 | 表示队列是否为空、是否已初始化等事实 |
| mutex | 协调访问相关共享状态的线程 |
| condition variable | 让条件不满足的线程等待，并接收重新检查的通知 |

**拿到锁不等于拿到元素。** C1 可以先拿锁、取走唯一元素、解锁，C2 随后拿到同一把锁，却发现队列为空。广播唤醒多人，不代表它们同时拥有锁。

队列为空也不等于所有任务已完成：某个任务可能已经被取走，正在锁外处理。`count` 通常只统计尚未领取的任务。

课程 [pc-cv-broadcast.c](../code/demos/concurrency/producer-consumer/pc-cv-broadcast.c) 用 `depth` 和打印括号模拟生产消费，没有真正存储元素内容；不要在那个示例里寻找不存在的任务对象。

### 3.3 条件变量的标准使用协议

```text
等待方：
    获得 mutex
    while 条件不成立：
        wait(cv, mutex)
    持锁执行依赖该条件的共享状态操作
    释放 mutex

改变状态的一方：
    获得同一把 mutex
    修改共享状态
    通知可能继续的等待者
    释放 mutex
```

`pthread_cond_wait(&cv, &m)` 必须在持有 `m` 时调用。它将释放锁与进入等待原子地衔接；解除等待后重新竞争锁，**重新持有锁才返回**。它不是“带着锁一直睡眠”。

条件变量不判断业务条件，不存储任务，也不积攒通知。**共享状态保存事实，通知只让等待者获得重新检查的机会。** C++ 条件变量规范同样要求返回时重新持锁，并把带谓词的等待定义为循环检查，见 [标准工作草案](https://eel.is/c++draft/thread.condition.condvar)。

本笔记采用状态修改和通知都放在锁内的模板，便于推理。不能由此推导“通知接口本身在任何设计下都必须持锁调用”；关键是共享谓词、等待与通知的完整协议正确。同一条件变量上的并发等待应使用同一关联 mutex。

### 3.4 为什么释放锁与等待必须原子衔接

如果消费者自己先解锁、过一会儿再进入等待，可能发生：

```text
消费者检查到 ready == false
消费者解锁
生产者拿锁，令 ready = true，通知并解锁
消费者这时才睡下，错过通知
```

如果以后没有新通知，消费者可能一直等待。这是丢失唤醒。正确的 `cond_wait` 协议消除释放锁与开始等待之间的这个空隙。

但“生产者在消费者开始运行前已经通知过”本身不是错误：如果生产者已经令 `ready = true`，消费者后来持锁检查时会直接通过，根本不调用 `wait`。**不需要睡眠的线程，也不需要被唤醒。**

### 3.5 为什么必须循环检查，而不是只写 if

需要处理两类情况。

第一，通知是真的，但条件在拿锁前已经改变。两个消费者被广播唤醒，C1 先拿锁取走唯一元素并解锁；C2 的 `wait` 返回时，锁在 C2 手里，队列却已经空了。

第二，接口允许虚假唤醒，即等待可以在没有与该次返回一一对应的显式通知时解除。底层实现中一次通知也可能造成额外等待者解除等待，程序不能依赖严格的一对一关系。

正常广播唤醒所有人，而部分人的条件不成立，并不需要归因于底层虚假唤醒；即使完全没有虚假唤醒，前一种竞争也已经足以要求重查。

```c
pthread_mutex_lock(&m);
while (count == 0) {
    pthread_cond_wait(&not_empty, &m);
}
/* 此刻持锁，并且刚检查到 count > 0，才能取元素。 */
pthread_mutex_unlock(&m);
```

**等待返回保证重新持有锁，不保证资源已经分配给你。** `if` 不会在返回后重新执行判断，`while` 才会。

一个具体的平台例子是：Solaris 文档记载，等待线程处理完某些操作系统信号后，条件等待可以成功返回，即使没有条件变量通知。操作系统 signal 与 `pthread_cond_signal` 是两种机制，不能混为一谈，也不能推断所有平台都以相同方式处理。[Oracle 官方说明](https://docs.oracle.com/cd/E36784_01/html/E36868/gen-24356.html)

### 3.6 signal、broadcast 与可直接阅读的有界队列

`signal` 至少唤醒一个等待者（存在等待者时），不保证选中业务上需要的那类；`broadcast` 唤醒所有等待者。它们都不会把关联 mutex 同时交给所有线程。

如果生产者和消费者都等在同一个 `cv` 上，只用 `signal` 可能唤错类型。例如消费者取走元素后，唤醒另一个消费者；后者检查为空又等待，而能够填入元素的生产者没有醒来。某些交错下所有人可能都在等待。**把 if 改成 while 解决重查，不自动解决通知对象选择。**

两种常见方案：一个条件变量配合广播；或者两个条件变量分别通知。下面采用第二种，完整补出实际存储整数的循环队列：

```c
#include <pthread.h>

#define CAPACITY 8

static int buffer[CAPACITY];
static int head = 0, tail = 0, count = 0;
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;
static pthread_cond_t not_full = PTHREAD_COND_INITIALIZER;

void put(int value) {
    pthread_mutex_lock(&m);
    while (count == CAPACITY) {
        pthread_cond_wait(&not_full, &m);
    }

    buffer[tail] = value;       // 真正的元素存储在这里
    tail = (tail + 1) % CAPACITY;
    count++;

    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&m);
}

int get(void) {
    pthread_mutex_lock(&m);
    while (count == 0) {
        pthread_cond_wait(&not_empty, &m);
    }

    int value = buffer[head];   // 真正读取元素内容
    head = (head + 1) % CAPACITY;
    count--;

    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&m);
    return value;
}
```

`head` 是下次取出的位置，`tail` 是下次放入的位置；取模让数组循环使用。代码维护 `0 <= count <= CAPACITY`，数组、下标和数量都由同一把 `m` 保护。两个条件变量仍然共用这一把锁。

这是不带关闭协议的基础队列。工程实现如果允许停止服务，需要增加 `closed` 等状态，把它纳入等待条件，并在关闭时唤醒相关等待者。线程拿到任务后通常在锁外处理，避免长计算占着队列锁。

### 3.7 计算图与工作线程池

计算图用节点表示任务，用有向边表示依赖。以 `A → B`、`A → C`、`B → D`、`C → D` 为例：A 完成后 B、C 可并行，D 要等 B、C 都完成。

一种实现是每个节点一个线程，等待“已完成前驱数等于前驱总数”。更实用的组织方式通常是固定工作线程池：依赖满足的任务进入就绪队列，空闲线程取任务执行，完成后更新后继的就绪状态。

**任务是要完成的工作，线程是执行工作的载体；一个任务不必对应一个新线程。** 图中节点的独立计算要放在同步临界区之外。

线程池把创建成本分摊到许多任务，但还需要队列容量、过载处理和退出协议。队列无限增长只会把处理能力不足转成内存和延迟问题；需要根据服务要求选择阻塞、拒绝或其他背压策略。

## 4. 信号量：保存并消费许可

### 4.1 P、V 与初始值的含义

**信号量是带计数的许可管理机制。** `P` 等待并原子地领取一份许可；`V` 增加一份许可。计数的业务含义由使用协议决定。

```text
初始 0：V → 1，V → 2，P → 1，P → 0，再 P 则等待
```

检查是否有许可和减一必须原子完成，不能让两个线程重复领取同一份许可。在课程接口中，`P` 对应 `sem_wait`，`V` 对应 `sem_post`；生产代码必须区分成功领取和错误返回。

条件变量的通知不积攒，事实要保存在外部状态中；信号量本身会保存尚未消费的许可。`V` 先发生，后来的 `P` 仍能领取。许可不等于实际数据：整数仍在缓冲区中，信号量只记录可领取的数量。

### 4.2 两种典型应用

**完成同步。** 信号量初值为 `0`，生产者写好数据后 `V`，消费者先 `P` 再使用数据。在正确配对协议下，这也建立数据交接所需的同步关系。D 要等两个前驱，就执行两次 `P`，两个前驱各完成一次 `V`。

**并发名额。** 信号量初值为 `N`，线程使用资源前 `P`，使用后 `V`，把同时使用者限制在 `N` 个以内。初值为 `1`、正确配对的 `P/V` 可以实现互斥，但不等于具备 pthread mutex 的全部语义。

mutex 通常有持有者约束，应由持有该 mutex 的线程解锁；信号量允许一个线程 `V`，另一个线程 `P`。信号量实现的“等待完成”也不等于完成了 `pthread_join` 的全部线程生命周期与资源回收职责。

### 4.3 信号量实现生产者—消费者

容量为 `N` 的缓冲区，初始化 `empty = N`、`fill = 0`。它们分别表示可领取的空位和可领取的数据元素。

```text
生产者：
    P(empty)               // 先预订一个空位
    lock(m)
    实际入队
    unlock(m)
    V(fill)                // 发布一份可取元素

消费者：
    P(fill)                // 先预订一份可取元素
    lock(m)
    实际出队
    unlock(m)
    V(empty)               // 归还一个空位
    在锁外处理数据
```

**信号量控制数量，mutex 保护一般队列的内部结构，两者职责不同。** 多个空位可以让多个生产者同时通过 `P(empty)`，它们仍可能竞争同一个队尾下标或链表指针。

不要拿着队列 mutex 再等 `P(fill)`：消费者在空队列上阻塞时，生产者也可能被这个 mutex 拦住，无法入队并 `V(fill)`。上面的协议先领取许可，再获取队列锁。

`empty + fill = N` 不是任意时刻都成立。生产者领取空位后、发布元素前，有一份许可处于在途状态；消费者也有对应阶段。只有没有在途许可时，两个可用计数的和才等于容量。

课程 [pc-sem/pc.c](../code/demos/concurrency/pc-sem/pc.c) 只打印括号，不维护真实队列，不应从它没有队列 mutex 推导出一般多生产者、多消费者队列也不需要互斥。

### 4.4 选择条件变量还是信号量

| 要表达的要求 | 自然的工具 |
|---|---|
| 等待初始化完成、队列非空或关闭等复合状态 | 共享谓词＋mutex＋条件变量 |
| 每完成一个任务就产生一份可消费凭证 | 信号量 |
| 同时使用资源的人数不超过 N | 信号量 |
| 操作一份共享结构时排他执行 | mutex；必要时与其他原语组合 |

两者都能通过更复杂的协议表达更多行为，不宜记成绝对的能力高低。区别是：单个信号量自然表达“有多少份许可”，条件变量则让程序直接等待一个共享状态谓词。

## 5. 并发 Bug：正确访问不等于正确业务

### 5.1 死锁与资源获取顺序

**死锁是一组线程互相等待这组线程才能完成的动作，导致它们无法继续推进。** 它与“持锁线程暂时没被调度”不同：后者可能通过重新调度持锁者取得进展，死锁不能仅靠轮流运行等待者解除。

典型 ABBA：T1 持有 A 等待 B，T2 持有 B 等待 A。哲学家各拿一把叉子、等待邻居手里的另一把，是更大的资源等待环。

在经典可复用排他资源模型中，分析四个必要条件：

| 条件 | 含义 |
|---|---|
| 互斥 | 资源不能由多个申请者同时占有使用 |
| 持有并等待 | 已占有部分资源，等待其他资源时仍不释放已有资源 |
| 不可抢占 | 已授予的资源不能被外部安全地强行收回，需要持有者按协议释放 |
| 循环等待 | 形成首尾相接的资源等待链 |

破坏其中任一必要条件，可以排除该模型下的资源死锁。这里的“不可抢占”说的是资源，不是 CPU 不能切换线程。多实例资源中，仅看到一个资源等待环也不能机械推出已经死锁。

工程上常通过统一锁序打破环：为锁规定严格顺序，所有路径都按同一顺序获取。只要持有较小编号的锁时只向更大编号申请，就不能形成编号严格递增却回到起点的环。该保证针对遵守协议的这些锁，不能包办程序内所有其他等待方式。

同一线程重复获取同一把非递归锁也有问题。对 pthread mutex，行为取决于 mutex 类型，可能自阻塞、返回错误或属于未定义行为，不能笼统说“任何 mutex 第二次加锁都一定死锁”。回调、递归和跨模块调用容易隐藏重复或逆序获取。

哲学家问题也可在同一管理 mutex 内检查并预订两把空闲叉子，或者限制拿叉子的竞争人数为 `N-1`。避免死锁不等于自动保证公平；饥饿是个别线程长期得不到机会，活锁则可能不断动作却没有有效进展。

### 5.2 三类非死锁问题

| 类型 | 需要检查什么 | 例子与修正方向 |
|---|---|---|
| Data race | 冲突访问有没有必要的同步关系 | 漏锁、上了不同锁；统一访问协议或正确使用原子操作 |
| 原子性违反 | 本应作为整体的步骤是否被插入 | 检查余额和扣款分别上锁；把整个操作纳入保护范围 |
| 顺序违反 | 事件是否按要求先后发生 | 使用先于初始化；等待初始化完成再使用 |

这些分类可以重叠。**原子性要求“这几步一起做”，顺序要求“先 A 后 B”。** 给每次读写加锁不能自动表达业务所需的整体性和先后关系。

例如，初始化线程和使用线程都拿同一把锁，虽然消除了配置字段上的 data race，使用线程仍可能先拿锁并读到初始状态。这需要增加“已初始化”的同步条件。

### 5.3 工具、测试和证明的边界

TSan 通过编译插桩与运行时分析检测数据竞争。常用构建选项为 `-fsanitize=thread -g`，但支持平台与实际开销依工具链而定；见 [Clang 官方文档](https://clang.llvm.org/docs/ThreadSanitizer.html)。课程 [race.c](../code/demos/concurrency/tsan/race.c) 展示“多数访问上锁，少数遗漏”仍然有问题。

lockdep 的核心思路是记录“持有 A 时申请 B”的依赖边，检测潜在锁依赖环。它不必等到一次运行真的发生 ABBA 才提示风险。课程用户态演示是简化实现，完整 Linux lockdep 还处理锁类、上下文等更多情况，见 [内核文档](https://docs.kernel.org/locking/lockdep-design.html)。

两者都不能代替业务正确性分析。数据竞争检测不自动理解“扣款前的余额检查必须持续有效”；运行未报告错误也不等于不存在未覆盖的问题。

**测试次数不能代替覆盖范围。** 一万次运行可能反复经过类似调度，而第 10001 次才遇到此前没有出现的错误交错。模型检查则是在模型有限、遍历和性质检查正确的前提下，穷尽可达状态来验证指定性质，例如不会两线程同时进入临界区。

必须分开两层：模型内部是否遗漏情况；真实实现是否符合模型假设。模型中的互斥性证明不自动包含编译器、语言和硬件实现的正确性，也不自动证明公平或所有活性性质。

Peterson 算法当前知道“在特定读写与顺序假设下实现两个线程互斥”即可。不要把普通共享 C 变量的直译当作可靠实现；也不要用一次成功运行替代对前提的检查。

## 6. 并行算法与数据结构：减少必须协调的事情

### 6.1 任务分解、粒度与负载均衡

**并行机会来自独立工作，实际收益来自合理的组织方式。** 计算图中的必要依赖不能靠增加核心取消；没有依赖的任务可以并行，但还需要足够的计算量摊薄管理开销。

Mandelbrot 的每个像素可独立计算，因此可以按区域分工。不能由此推出每像素创建一个线程：`6400 × 6400` 图像有 4096 万个像素，而线程需要栈、管理信息和调度资源。

固定数量的工作线程可以连续处理许多区域块。块太小，任务领取和同步开销大；块太大，可能分工不均。像素数量相同不代表计算时间相同，Mandelbrot 不同像素的迭代次数就可能不同。

OpenMP 提供共享内存并行编程支持；MPI 提供消息传递编程支持，当前知道用途即可。`#pragma omp parallel for` 表示分工执行循环；只有 `parallel` 不能自动让后面的普通循环迭代分摊给各线程。课程实际 [mandelbrot.c](../code/demos/concurrency/mandelbrot/mandelbrot.c) 使用了 `omp parallel` 和 `omp for`。

线程数、任务粒度和调度策略都依赖负载。CPU 密集型工作不应只靠增加线程数优化；阻塞等待较多的工作则可能从更多并发请求中获益。不能脱离可用核心、阻塞比例、内存和尾延迟要求，给出所有程序通用的“最佳线程数”。

### 6.2 先减少共享更新，再考虑更快的锁

如果只要求最终整数总和，可以让线程各算自己的区间，最后合并：

```text
各线程：只读输入，在线程自己的 local 中累计，写入自己的 partial[tid]
主线程：join 全部工作线程后，合并 partial
```

这里假设数值范围合适且分区覆盖正确。线程私有累计避免每处理一个数就争用同一个 `sum`。即使换成原子加法，同一个全局计数器仍是共同更新点，需要跨核协调，可能成为性能瓶颈。

本地累计改变了中间状态的可观察性。如果其他线程需要随时得到精确全局总数，就不能直接用“最后合并”替换。

### 6.3 TLS 与批量合并

**TLS 是每个线程各有一份、可跨函数调用保留的状态。** 普通自动局部变量的生存期由所在代码块的一次执行决定；TLS 对象具有线程存储期。`thread_local` 并不让所有线程共享一个全局对象。

课程 [tls.c](../code/demos/concurrency/tls/tls.c) 按 C23 编译：四个线程各自把 `thread_local int x = 100;` 加一，观察到各自地址不同、值均为 `101`。这是一次具体运行的观察，独立副本则来自语言语义。

实现上可以理解成“当前线程 TLS 基址＋变量偏移”。x86-64 常借助 FS base，具体段布局和指令当前不必背。课堂注释里的块作用域声明限制针对 C 的规则，不应直接套到 C++。

若运行期间需要持续计数，但允许全局显示暂时滞后，可以批量合并：

```c
#include <pthread.h>

static thread_local unsigned pending = 0;  // C23
static unsigned long long sum = 0;
static pthread_mutex_t sum_lock = PTHREAD_MUTEX_INITIALIZER;

void flush_pending(void) {
    if (pending == 0) return;
    pthread_mutex_lock(&sum_lock);
    sum += pending;
    pthread_mutex_unlock(&sum_lock);
    pending = 0;
}

void increment(void) {
    if (++pending == 100) flush_pending();
}
```

大约每 100 次计数才争用一次全局锁；它不承诺把总运行时间缩短 100 倍。运行期间，全局 `sum` 没有包含尚未提交的余量。需要最终精确时，每个工作线程应在退出前执行 `flush_pending()`，主线程再 `join` 并读取。读取全局 `sum` 也应遵守正确同步协议。

**允许值滞后是业务语义的放宽，不是允许 data race。** 也不能仅因用了本地缓存就声称自动获得“最终一致性”：余量提交、线程结束和故障处理必须有明确协议。

点赞计数可以作为这个设计的应用例子：每个线程暂存同一帖子的增量，再批量合并。真实数据仍需按帖子区分，TLS 不属于某个用户，线程池也会复用线程；跨请求状态要明确清理或重新设置。TLS 不提供持久化，尚未提交的数据可能随进程退出丢失。这是设计示例，不是对某个平台内部实现的断言。

另一个性能边界是**伪共享**：线程虽然修改不同变量，但变量位于同一缓存行，仍可能因缓存一致性通信互相拖慢。它不是 data race。只有测量确认后，再考虑布局、填充或分块；具体缓存行大小不能当成语言保证。

### 6.4 分桶锁、读写锁与整体结构变化

数据结构分散存储，操作一个局部未必需要锁住全部结构。例如采用每桶独立链表的哈希表，可以给每个桶一把锁。更新不同桶的记录能够并行，同桶的不同 key 仍可能排队。

以演示用的 `post_id % 4` 为例，101 和 105 都落到桶 1，202 落到桶 2。**不同 key 不保证不同锁；锁的粒度决定哪些操作仍然互斥。** 哈希表的常数时间通常指合适哈希和负载条件下的平均表现，不能当作最坏情况保证。

读写锁允许多个读者共存，写者与读者、写者互斥。是否比 mutex 更快取决于读写比例、临界区长度及实现开销；读多不自动等于一定获益，也不自动保证公平。

扩容会改变桶数组大小、记录位置和数组生命周期，单个桶锁不够。一个容易推理的设计是两层保护：

```text
普通操作：结构读锁 → 定位桶 → 桶锁 → 操作记录 → 解桶锁 → 解结构读锁
扩容操作：结构写锁 → 搬迁／替换数组／释放旧数组 → 解结构写锁
```

这里普通更新也能持有“结构读锁”：它只读取、使用桶数组的布局，没有改变布局；具体记录的修改另外由桶锁保护。所有访问都遵守此协议，扩容拿到结构写锁后，才能排除仍使用旧数组的普通操作。

统一先结构锁、后桶锁。不能持有桶锁后再等待结构写锁，也不能想当然地原地升级读锁：可能与“持结构读锁、等桶锁”的线程互相等待。需要扩容时，应按设计释放当前锁、重新申请并重查条件。

开放寻址的探测、删除、墓碑和遍历会跨越更多存储位置，不能直接照搬“每桶独立链表”的局部锁证明。当前重点是：**先识别一次操作涉及的状态和不变量，再选择互斥范围。锁拆得更细，协议也更复杂。**

### 6.5 性能分析怎样落到实验

先固定问题与工作总量，再比较线程数和实现，重复测量。至少关注吞吐量、延迟、CPU 使用和争用，而不是只看某次“跑得更快”。尾延迟对服务场景尤其重要。

课程 [sum-experiment](../code/demos/concurrency/sum-experiment/README.md) 对比自旋锁、mutex 和原子更新，并改变线程数。它主要研究共享计数器争用，不代表所有应用里某种锁都更快。每次结果都应联系机器、工具链、总工作量和负载解释。

优先检查顺序：有没有不必要的共享更新；能否本地计算和批量合并；任务粒度与负载是否合适；是否需要缩小锁范围；最后再针对已测得的瓶颈选择具体原语。

## 7. 面试自测：把结论解释到机制

以下是通用基础题的答题骨架。目标是能解释“为什么”和适用条件，不是只背术语。

| 问题 | 回答必须包含的关键点 |
|---|---|
| 单核为什么也有并发错误？ | 读—改—写可以被线程切换打断，不需要物理上同时执行 |
| 同进程线程共享什么，独立什么？ | 地址空间和共享资源；各自执行状态、寄存器、栈；独立栈不是内存隔离 |
| 为什么 `i++` 不一定原子？ | 通常涉及读取、计算、写回；源码一行不等于一个原子操作 |
| 原子变量就能保证整个业务安全吗？ | 单次原子操作不自动合并多个步骤，不自动解决跨对象不变量和资源生命周期 |
| 原子性、可见性、顺序分别是什么？ | 操作是否可分割、同步后哪些写入可被观察、操作间需满足哪些关系；不能靠普通缓存直觉代替内存模型 |
| C／C++ 的 volatile 能代替锁吗？ | 不能提供通用线程同步或复合操作原子性；别与 Java volatile 混用定义 |
| 为什么所有读写加锁，余额仍可能错？ | 检查和扣款需要整体保护，分别加锁仍允许中间状态变化 |
| 自旋锁与 mutex 怎么选？ | 区分语义与等待策略，结合等待时长、核心占用、抢占和阻塞唤醒成本 |
| 每次加 mutex 都要进入内核吗？ | 不一定；用户态快路径与竞争时的 futex 等待是不同路径 |
| 为什么 `cond_wait` 要关联 mutex？ | 持锁检查共享谓词，原子衔接解锁与等待，返回前重新持锁 |
| 为什么条件变量使用 while 而非 if？ | 资源可能先被别人取走，也可能虚假唤醒；醒来后条件不保证成立 |
| 广播后所有消费者都拿到锁和元素了吗？ | 只是解除等待，仍须先后竞争同一把锁，再检查有没有元素 |
| 通知发生在等待前一定会丢失唤醒吗？ | 不一定；状态若已成立，后来检查可直接通过；危险的是检查假与入睡间留下空隙 |
| signal 与 broadcast 怎样选择？ | 等待者条件是否一致、要放行多少人；不同条件共用 cv 要防止唤错类型导致停滞 |
| 条件变量与信号量区别是什么？ | 条件变量通知不积攒，谓词在共享状态里；信号量保存可消费许可，成功 P 会领取一份 |
| 有两个计数信号量还要队列锁吗？ | 一般需要；许可管理数量，不能自动保护多线程修改队首队尾等结构 |
| 死锁四条件、ABBA、锁序怎么解释？ | 说明资源模型，区分资源不可抢占与线程可抢占，用等待环解释固定锁序 |
| 没有 data race 是否就正确？ | 不一定，还可能违反操作原子性、事件顺序或发生死锁 |
| 为什么线程更多反而更慢？ | 串行比例、共享热点、调度通信、缓存和带宽限制，以及任务过细或负载不均 |
| 为什么不每个像素创建一个线程？ | 任务与执行线程分离，管理成本和资源占用要由足够计算量摊薄 |
| TLS 属于线程还是用户？ | 属于线程，池化线程会处理不同任务／用户；不提供请求隔离或持久化 |
| 批量计数最终会自动准确吗？ | 不自动；剩余增量须提交，读取要同步，退出和故障处理需有协议 |
| 不同 key 就可以无锁操作哈希表吗？ | 不保证，可能同桶、跨桶操作或遇到扩容；需先识别共享结构与生命周期 |
| 已有桶锁，为何扩容还要协调？ | 桶数组和记录位置会变化，旧数组不能在仍有访问者时被释放 |
| 压测没出错能证明正确吗？ | 不能；观察轨迹不是全部轨迹，工具和模型证明也都有明确范围 |

准备手写或口述题时，优先做到：能写第 3.6 节有界队列；能解释信号量版本的 P/V 顺序；能给出一个 ABBA 轨迹与固定锁序修正；能用“检查—使用”解释没有 data race 仍会出错；能从共享热点解释扩展性差。

语言专属并发库应另行准备。C++ 的 RAII、标准原子与条件变量，Java 的 JMM、锁、线程池与 ThreadLocal，Go 的 goroutine 与 channel，不能仅靠本笔记互相类推。

课堂示例可能故意保留错误。`cgraph-mutex` 用其他线程解锁 mutex 的方式演示依赖，不能当作合法 pthread 协议；Mandelbrot 的实时预览还直接读取计算线程正在写的非原子图像数据，计算任务独立不代表整份示例没有数据竞争。阅读时应区分教学目的、语言保证、平台实现和一次运行观察。

本次示例验证使用 GCC 15.2、C23 和 pthread：有界队列在容量 1、8、31 下分别运行了单生产者／单消费者及四生产者／四消费者，检查 FIFO 或元素无丢失、无重复；TLS 批量计数验证了四个线程各累计 137 次并提交余量后，总数为 548。运行检查用于发现实现错误，不代替对所有允许执行的正确性分析。

## Recap

先识别共享状态、不变量与依赖，用互斥保护整体、用同步规定先后，再分别检查数据竞争、逻辑错误和死锁。性能优化优先减少共享与同步，随后才是选择更细的锁和更复杂的原语；所有结论都需要保留模型、语言和负载条件。
